## Пункт 2. Сравнение версий и поиск изменений

### Разница между командами

- `git log` (с флагом `--stat`) показывает хронологию коммитов и статистику изменений. Это «летопись» проекта.
- `git diff` показывает построчную разницу между версиями (строки с `-` и `+`).
- `git show` раскрывает детали одного конкретного коммита: сообщение автора и сам diff.

### Результаты поиска

- `git log -S"def"`: Найдена история изменений ключевого слова. Результат: коммит `426e933` (`feat: add calc.py with basic operations`). Это доказывает, что поиск по содержимому кода работает.
- `git blame lab03/calc.py`: Показано, что все строки файла `lab03/calc.py` были добавлены в коммите `426e933`. Это подтверждает, что файл был создан целиком в рамках этой лабораторной работы.
## Пункт 3. Восстановление файла

### Разница между командами

1. **`git restore <file>`** (без указания источника):
   - Восстанавливает файл из **последнего коммита** (`HEAD`).
   - Используется, чтобы отменить **локальные незакоммиченные правки** (если случайно что-то удалил или испортил).
   - Мои правки, сделанные в Шаге 1, были полностью потеряны при выполнении этой команды.

2. **`git restore --source=HEAD~2 <file>`**:
   - Восстанавливает файл из конкретной точки истории (в данном случае — коммит, который был **два шага назад**).
   - Позволяет откатиться не просто к «вчерашнему дню», а к «позавчерашнему».
   - Если бы я сделала коммит с испорченным файлом, эта команда помогла бы мне откатиться на 2 коммита назад, игнорируя последний.

### Что произошло с моими правками

- При выполнении `git restore lab03/calc.py` мои локальные изменения (удалённые строки) были безвозвратно удалены. Git вернул файл в состояние последнего коммита.
- При использовании `--source=HEAD~2` я увидела, как файл выглядел раньше. Это полезно, если в последнем коммите была допущена ошибка, и нужно вернуть состояние из более ранней версии.## Анализ git revert vs git reset

### Что такое git revert?

`git revert` — это команда, которая **создаёт новый коммит**, изменения в котором противоположны изменениям в отменяемом коммите.
*   Пример: если в коммите А мы добавили строку `x = 10`, то `revert` создаст коммит Б, который удалит эту строку.
*   В истории остаются оба коммита: и ошибочный, и отменяющий.

### Чем это отличается от git reset --hard?

| Характеристика | `git revert` | `git reset --hard` |
| --- | --- | --- |
| **Влияние на историю** | История сохраняется. Добавляется новый коммит. | История **переписывается**. Коммиты удаляются из ветки. |
| **Хэши коммитов** | Хэши старых коммитов **не меняются**. | Хэши последующих коммитов **меняются** (так как у них меняется родитель). |
| **Безопасность в команде** | **Безопасно**. Можно пушить в общий репозиторий. | **Опасно**. Нельзя пушить в общий репозиторий без согласования, так как это сломает историю у коллег. |

### Почему revert безопаснее в опубликованной истории?

Если ветка уже отправлена на сервер (`git push`) и другие разработчики скачали её:
1.  При использовании `git reset --hard` и последующем `push` потребуется принудительная отправка (`--force`). Это перезапишет историю на сервере, и у коллег их локальные ветки рассинхронизируются. Им придётся вручную восстанавливать свою работу.
2.  При использовании `git revert` история просто дополняется. Обычный `git push` сработает без проблем, и все участники команды получат корректное исправление без конфликтов истории.

**Вывод:** `revert` — это правильный способ исправления ошибок в общей истории, так как он уважает работу других разработчиков и сохраняет целостность истории проекта.
